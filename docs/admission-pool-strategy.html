零、最高优先级：评测结果 UI 改造

P0+ · 全项目最高优先级 — 在修 Rubric、跑分逻辑之前，先把「可解释性分析 + 人工校验」改成两级标签单焦点展示，否则 8 session × N 指标平铺会导致人工打标错乱，无法积累高质量入池标定数据。

现状问题（对应截图红框区域）

当前 NotebookLayout 的「评测结果 → 可解释性分析」将所有 session 的全部维度结果平铺在同一滚动区内；下方「人工校验队列」又以 metric 为粒度再次平铺。8 个 session × 3 个二级指标 ≈ 24 张卡片堆叠，审阅者很难对齐「这条会话在这个指标上该怎么判」。

目标信息架构

层级控件内容
一级标签 Session ID 横向 Tab（case_001…） 切换后加载该 session 的总览与 transcript；显示综合分 / tier / 待审数量角标
二级标签 二级指标 Tab（任务完成度、筛选决策…） 只展示当前 session × 当前指标的评测详情与人工校验表单
内容区 A 原始会话（默认折叠） 来自 case.input.transcript；展开后可对照证据
内容区 B 本 Session 评测总览 case 级加权分、Q 分、tier、各指标迷你条 / 雷达摘要
内容区 C 单维度评测详情 score / confidence / reason / evidence / rubricForm 对照
内容区 D 人工校验板块 认可 / 驳回 / 补证据 + 备注；绑定 channel；单条或批量入池

与现有代码的集成点

  • 改造位置：NotebookLayout.tsx 中 BenchmarkResultPanel 的「可解释性分析」+「人工校验队列」合并为同一两级 Tab 容器。
  • 数据源：props.result.cases + metricResults 按 caseId × metricKey join；humanReviewRecords 键为 submissionId + metricKey（已有）。
  • 顶部「主要能力短板 / 最需关注指标」保留为全局摘要，不再与 per-case 列表混排。
  • 「保存入池」从底部批量按钮改为：当前 Tab 下「保存本条」+ 顶部「保存本 session 全部已审」。
验收标准 审阅者无需滚动即可在单一视图内完成「读会话 → 看该指标评分 → 下判断 → 入池」闭环；切换 session / 指标时上下文不丢失、不串台。

一、核心结论

当前 100% 平均分不代表模型或对话真的好，而是评测链路对「通过」过于宽松，区分度被压扁了。在修复评测粒度之前，不建议用本次结果做入池或 reRank。

直接判断 问题来自两层：上游首轮 Rubric 只生成 3 个二级指标（2 个能力维度），评测维度严重不足；下游两个规则指标虚高 + LLM judge 偏松 + 聚合太粗 → 8 个 case 全部 100%，goodcase 池会充满「假金标」。

二、为何现在全是 100%？

根因分两层：上游首轮 Rubric 仅 3 个二级指标，评测维度太少（详见二（补））；下游现有三条指标路径都倾向于给满分，再经加权平均后全部顶格。

二级指标评测器实际行为典型得分
任务完成度 task_success llm_judge 无金标时 LLM 倾向「解释得好」→ 给 5 分；rubricForm 5/3/1 档未强制对照 5 / 5
筛选决策准确率 decision_accuracy exact_match case 无 expected 字段 → undefined === undefined → 直接匹配 5 / 5
输出格式合规性 output_schema_valid regex_match 被测 prompt 强制 JSON 输出，正则 \{[\s\S]*\} 几乎总过 5 / 5

其他加剧因素

  • 评的是新生成答案，不是历史对话 — generic-run 让 LLM 读 transcript 后写 JSON 分析报告，而非评 assistant 真实轮次。
  • MVP 只抽 8 个 session — 20 条数据中仅评前 8 条（MAX_DATASET_CASES = 8）。
  • 入池阈值二元化 — <60 badcase，≥90 goodcase，中间区间直接丢弃，无 tier 区分。

二（补）、首轮 Rubric 指标过少 — 上游根因

区分度不足不仅发生在跑分阶段，更早在评分标准生成阶段就已埋下：第一轮 draftBenchmarkRubric 往往只产出 2 个能力维度 · 3 个二级指标，对情绪陪伴这类复杂场景远远不够。

现状快照（本次任务） 一级维度仅「任务完成」「格式合规」；二级指标仅「任务完成度」「筛选决策准确率」「输出格式合规性」。缺少共情、流失信号、互动连续性等该领域核心验收维度，导致 reRank 与 Channel 学习都缺少可用的特征向量。

为何首轮容易偏少？

环节现象影响
draftBenchmarkRubric Prompt 要求 4–10 个指标，但 LLM 首轮常取保守下限；用户未追问时不再扩充 能力覆盖面窄，遗漏领域关键维度
能力维度选择 默认偏向通用的 task_completion + format_compliance 情绪陪伴场景的共情、留存、安全等维度未进入图谱
评测器类型 混入 exact_match / regex 等规则指标，但无金标时无效 占用了指标名额却不贡献真实区分度
用户确认流程 「确认全部」后不再迭代 Rubric，直接开跑 稀疏 Rubric 被固化进整条 pipeline

解决方案（Rubric 生成层）

生成策略

首轮就要够宽

  • 按场景模板设定最低指标数（建议 ≥6，复杂场景 ≥8）
  • 每个能力维度至少 2 个二级指标，覆盖「做得好」与「做得差」两侧
  • 优先 llm_judge，无金标时禁用 exact_match
  • DeepSearch brief 必须映射到具体指标，不能只写进 researchSummary
交互策略

生成后强制扩充一轮

  • Rubric Agent 自动检查：指标数 < 6 时提示「维度不足」并建议增补
  • 按业务需求（如 DAU/流失）追问缺失维度，再生成第二轮指标
  • 图谱 UI 展示「建议补充」虚线节点，用户一键采纳
  • 开跑前门禁：approvedMetrics.length < 6 时警告
与下游的关系 Rubric 指标数量 = reRank 的特征维度数 = Channel 数量上限。3 个指标最多 3 条 Channel，即使跑分逻辑完美，也无法在 goodcase 内做细粒度排序，更无法学到有意义的 per-channel 分布。

四、Good case reRank 方案

目标：即使同样「通过」的 case，也要能排先后，回答「到底有多好」。

质量分 Q（case 或 session 级） Q = Σ (wᵢ × norm_scoreᵢ × confᵢ) − λ × disagreement_penalty
因子含义数据来源
norm_scoreᵢ二级指标归一化分（用 rubricForm 档位，非二值）evaluators 改造后
confᵢ该指标评测置信度LLM judge 已有 confidence
wᵢ图 3 指标权重rubric weight 3/4/2
disagreement_penalty多指标分歧、低置信、需人工复核时扣分metricResults 聚合

建议写入 case 元数据的字段

qualityScore, qualityTier (gold | silver | borderline),
rankInRun, metricVector, confVector

六、类 RLHF 学习路径（100 条人工标定）

当积累约 100 条人工校验队列入池数据后，按 channel 学习分数分布特征，逐步建立自动化入池规则。本方案采用静态规则 Policy（见七（补）），不训练 reward 小模型。

三步实施

Step 1 · 标定

人工标定 Schema

  • sessionId + channel
  • humanVerdict: accept / reject / needs_evidence
  • qualityTier: gold / silver / reject
  • 各二级指标人工分 1–5 + notes
Step 2 · 学习

每 Channel 估计分布

  • P(score | accept) vs P(score | reject)
  • confidence 与 accept 率关系
  • qualityScore 百分位动态阈值
  • 自动分 vs 人工分一致率（校准 judge）

产出物：Channel Admission Policy（示例）

{
  "channel": "ch_task_completion",
  "version": "admission-policy-v1",
  "acceptRules": [
    { "metric": "task_success", "scoreGte": 4, "confidenceGte": 0.75 },
    { "qualityPercentileGte": 0.6 }
  ],
  "rejectRules": [
    { "metric": "task_success", "scoreLte": 2 }
  ],
  "sampleRateForHuman": 0.3
}

七、自动化入池引擎（概念架构）

收敛建议 将 eval-datasets/admission/pipeline.ts（主 evaluate 五通道）与 benchmark/case-admission.ts（Benchmark 人工入池）统一为同一套 Policy 接口，避免两套逻辑分叉。

七（补）、人工标定 → 静态入池 Policy（不训练小模型）

在两级标签 UI中完成人工校验后，将标定记录聚合为可版本化的静态规则 JSON，供后续 run 自动建议入池决策。全程用统计分位数 / 阈值拟合，不训练入池小模型。

标定记录 Schema（与 UI 两级标签对齐）

{
  "reviewId": "rev_...",
  "runId": "benchmark_generic_...",
  "caseId": "rubric_custom_..._case_001",
  "sessionId": "companion_pos_001",
  "metricKey": "task_success",
  "channel": "ch_task_completion",
  "decision": "accepted",
  "qualityTier": "silver",
  "autoScore": 3.6,
  "autoConfidence": 0.71,
  "reviewer": "user_001",
  "note": "识别了局限但建议不足",
  "reviewedAt": "2026-06-10T..."
}

静态 Policy 生成算法（纯统计，无模型训练）

对每个 channel，将人工标定样本分为 accept 与 reject 两组，提取特征并拟合规则：

特征字段accept 组统计reject 组统计产出规则
autoScore（0–5） P20 分位数 P80 分位数 scoreGte / scoreLte
autoConfidence 中位数 — confidenceGte
qualityScore（reRank 后） P30 百分位 — qualityPercentileGte
人工与自动一致率 按指标统计 — 低一致率 → 提高 sampleRateForHuman

Policy JSON 示例（静态、可审阅）

{
  "policyId": "admission-policy-v1",
  "projectId": "default",
  "generatedAt": "2026-06-10T12:00:00Z",
  "labelCount": 128,
  "channels": {
    "ch_task_completion": {
      "acceptRules": [
        { "metric": "task_success", "scoreGte": 4, "confidenceGte": 0.72 },
        { "qualityPercentileGte": 0.55 }
      ],
      "rejectRules": [
        { "metric": "task_success", "scoreLte": 2 }
      ],
      "uncertaintyRules": [
        { "confidenceLt": 0.65 },
        { "scoreBetween": [2.5, 3.5] }
      ],
      "sampleRateForHuman": 0.25,
      "stats": { "acceptN": 64, "rejectN": 22, "agreementRate": 0.81 }
    }
  }
}

在当前 UI 中的集成方式

评测结果页

人工校验时

  • 两级标签内展示当前 Channel 与 Policy 建议（若有）
  • 人工决定覆盖 Policy 建议，写入 humanReviewRecords
  • 顶栏显示「已标定 N / 目标 100」进度条
标定达标后

生成 Policy

  • 「生成入池策略」按钮（N≥100 可点）
  • 弹窗预览各 Channel 规则 + 覆盖率模拟
  • 确认后写入 PolicyStore，显示版本号 v1
后续 Run

自动建议

  • 跑分完成后 AdmissionScorer 预填建议
  • 高置信命中 acceptRule → 绿色「建议入池」
  • 命中 uncertaintyRule → 仍进人工队列（与现网一致）
模块边界

建议新增

  • src/benchmark/admission-policy-learner.ts — 纯函数统计
  • src/benchmark/admission-policy-store.ts — 读写 JSON
  • src/benchmark/admission-scorer.ts — 规则求值
与 RLHF 的边界 人类标定 = preference signal；静态 Policy = 手工可读的 reward 规则表；版本化发布 = 策略更新。不需要训练神经网络，标定满 100 条即可产出 v1，后续增量标定离线重算 v2。

八、分阶段实施优先级

优先级事项说明
P0+ 评测结果两级标签 UI Session ID → 二级指标；单 session 焦点 + 人工校验入池；全项目最高优先
P0 修 Rubric + 跑分区分度 最低 6 指标、禁用空 expected、rubricForm 强制、评 transcript 本体
P1 reRank + 标定 schema Q 分 / qualityTier；与两级 UI 的人工校验字段对齐
P1 静态 Policy 管线 标定 ≥100 条 → 统计生成 JSON → 后续 run 自动建议；不训练小模型
P2 Channel 规则收敛 与 evaluate 五通道统一 Policy 接口；低置信进 uncertainty 队列
P0+ · 最高优先

评测结果两级标签 UI

  • 合并「可解释性分析」与「人工校验队列」
  • 一级 Tab：Session ID；二级 Tab：二级指标
  • 内容区：原始会话（折叠）+ 总览 + 单维度 + 人工校验
  • 单条 / 单 session 入池，避免平铺错乱
P0 · 立刻

修 Rubric + 评测区分度

  • 首轮 Rubric 最低 6 指标门禁，无金标禁用 exact_match
  • Rubric Agent 自动提示维度不足并建议增补
  • LLM judge 强制按 rubricForm 打分
  • 支持「评 transcript 本体」模式
P1 · 短期

reRank + 静态 Policy 准备

  • 实现 Q 分与 qualityTier
  • 标定记录写入 channel / qualityTier 字段
  • 「生成入池策略」按钮 + Policy 预览弹窗
P2 · 中期

静态 Policy 上线

  • 100 条标定 → admission-policy-v1.json
  • AdmissionScorer 自动建议入池
  • 增量标定离线重算 v2、v3
