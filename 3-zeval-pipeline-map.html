3
Bad Case 抽取
buildBadCaseAssets · 规则打分 · LLM 结果作为输入
打分逻辑 = 白盒 goal/recovery = 黑盒输入
🏷️Tag 打标（白盒规则）
  • goal_failed — goalCompletion.status=failed (+0.34)
  • goal_partial — goalCompletion.status=partial (+0.20)
  • goal_unclear — goalCompletion.status=unclear (+0.12)
  • recovery_failed — recoveryTrace.status=failed (+0.24)
  • question_repeat — 相同问题出现≥2次 (+0.18)
  • understanding_barrier — 正则："什么意思|不懂|再说一遍" (+0.16)
  • escalation_keyword — 正则："转人工|投诉|主管|经理" (+0.22)
  • long_response_gap — responseGapSec ≥ 60s (+0.10)
📊severityScore 合成（混合）

加法叠加：各 tag 对应固定权重，累加后排序。

high → baselineScore 0.2 medium → 0.4 low → 0.6
⚠ 白盒弱点：权重固定在代码里，不同业务场景下"升级比目标失败更严重"无法动态调整。
黑盒输入：goal/recovery 的 status 来自 LLM，权重却是白盒规则。这是整个链路中黑白盒交界最密集的一层，也是当前体系最脆弱的地方——LLM 判错一个 goal_failed 会直接影响 severityScore。

五通道准入 Pipeline
eval-datasets/admission · 自动去重 · 沉淀入 DatasetStore
规则通道 = 白盒 置信度阈值 = 黑盒相关 待审通道 = 人工介入
TP · auto_tp
已被 badCase 抽取器确认为 bad + 准入规则触发
auto_admitted
规则：goal_failed / low_empathy / off_topic_high / preachy_high / recovery_failure 等 8条
FN · auto_fn
检测器未标 bad，但行为信号异常（漏检）

规则：dropoff_negative_tail / repeated_question / length_collapse / consecutive_short
TN · auto_tn
高质量正样本：goal_achieved + 高置信 + 高共情，或随机抽样（5%）
auto_admitted ✓

Uncertainty
LLM 置信度落在 [0.4, 0.6] 区间，判断不稳定

Human
DatasetConsole 手动标注，绕过自动通道直入数据集
human_labeled
最高可信度来源，用于纠正自动通道的系统性偏差

数据集管理 · 人工审核层
DatasetStore · reviewStatus 流转 · DatasetConsole "待确认" tab
pending_review = 必须人工参与 auto_admitted = 自动流入
🗃️DatasetCaseRecord 字段
  • caseSetType — badcase / goodcase
  • source — 来源通道（auto_tp/fn/tn/uncertainty/human）
  • reviewStatus — auto_captured → confirmed / rejected
  • normalizedTranscriptHash — 去重键
  • baselineCaseScore — 基准分（severity 映射）
  • tags[] — 能力标签
  • autoSignals[] — 触发规则列表
👤人工审核（白盒介入点）

需要人工操作的两类 case：

  • FN 通道：系统认为是漏检，需确认是否真 bad
  • Uncertainty 通道：LLM 自信度低，需人工定夺
⚠ 关键白盒点：如果跳过人工审核，FN 和 Uncertainty 案例直接以 auto_captured 状态留存，不会自动进入 benchmark——需要人工 confirm 才算进测试集。
↓
6
Benchmark 测试集构建
badcase pool + goodcase pool → 能力维度测试集
tag 分层 = 白盒 case 确认 = 人工
🎯Badcase Pool（失败回归集）
  • 来源：TP（auto_admitted）+ 人工 confirmed FN/Uncertainty
  • 按 tag 分层对应能力维度：
goal_failed → 目标达成能力 understanding_barrier → 理解能力 recovery_failed → 恢复能力 escalation_keyword → 情绪管理 low_empathy → 共情表达 off_topic_high → 话题对齐 preachy_high → 语气克制
✨Goodcase Pool（黄金正例集）
  • 来源：TN（auto_admitted）+ 人工 confirmed 优质 case
  • 用途：正样本对比、回归基准
  • baselineCaseScore = 0.9（固定）
⚠ 当前限制：tag taxonomy 固定在代码里（BadCaseTag 枚举），新增能力维度需改代码，无 UI 配置入口——这是一个典型的"白盒但僵硬"问题。
↓
7
动态回放验证
intentExtract → SimUser replay → intentMetrics
意图提取 = LLM SimUser = LLM Agent agent endpoint = 人工配置
🔍intentExtract（黑盒）

LLM 从历史 session 提取意图序列：

  • intentText — 意图描述
  • turnSpanUserTurns — 覆盖轮次范围
  • exampleUserQueries — 示例追问
  • successCriteria — 成功判断标准
temperature ≤ 0.3，seed=42（确定性），并发 = 4 session
🤖SimUser Replay（混合）

用提取的意图驱动 SimUser 向真实 Agent 发问，记录对话流程。

  • agentApiEndpoint — 白盒：人工提供
  • SimUser 对话策略 — 黑盒：LLM 生成
  • intentMetrics — 完成率 / 偏差率
↓
8
修复包与回归验证
RemediationPackage → ValidationRun → before/after 对比
指标对比 = 白盒 修复策略 = 人工决策
📦RemediationPackage（白盒）
  • 根据 bad case 池 + 指标生成改进建议
  • 关联触发这批 bad case 的规则 key
  • 链接到对应的 benchmark test set
🔁ValidationRun（白盒）
  • replay / offline_eval 两种模式
  • 对修复后的 agent 重跑 benchmark
  • 输出 before/after 指标 delta
  • 回归判定标准需人工定义

阶段 黑盒节点（LLM / 自动编码） 白盒节点（规则透明 / 人工介入） 当前局限 / 改进建议
数据富化 — 全部白盒（正则 + 时间差） isQuestion 正则较粗，可接入分词增强
客观指标 — 全部白盒（11 个规则指标） agentResolutionSignalRate 正则覆盖面窄
主观 · 信号层 — implicitSignals 全部白盒 信号 key 固定在代码，业务方无法自定义
主观 · goalCompletion LLM 判断 unclear 状态 规则先判 achieved/failed 条件 unclear 定义模糊，LLM 一致性较低
主观 · recoveryTrace LLM 生成 repairStrategy failure/recovery point 检测为规则 repairStrategy 文本无结构化验证
主观 · 三维度评分 完全 LLM Judge 维度名称和描述由人定义 per-session 分数无法回溯到具体 turn
扩展指标 9 个 LLM 指标，无限速 toolCorrectness 为规则 无并发限制，大批量易打爆 provider
Bad Case 打分 goal/recovery 输入来自 LLM Tag 规则 + 固定权重全白盒 权重写死在代码，不同场景无法配置
TP 准入规则 empathy/offTopic/preachy 阈值依赖 LLM 分 阈值（≤2）写在代码可直接看 聚合分（非 per-session）用于 TP 判断，精度损失
FN 准入规则 — 4 条规则全白盒（正则/统计） fn_consecutive_short 阈值（≤5字）太宽松
TN 准入规则 goal_achieved + confidence 依赖 LLM sampleRate(5%) 固定可配 随机采样的正例质量无保障
Uncertainty 通道 LLM confidence ∈ [0.4, 0.6] 区间阈值写在代码可调 置信度本身是 LLM 自报，不可全信
人工审核 — DatasetConsole 待确认 tab
confirmed / rejected 操作		 目前无审核 SLA / 漏审检测机制
Tag Taxonomy — BadCaseTag 枚举固定 ⚠ 最僵硬处：增加新维度需改代码，无 UI 配置

关键洞察
🔴最集中的黑盒风险

goalCompletion → severityScore → 准入通道这条链路。

LLM 一旦错判 goal_failed，会导致：severityScore +0.34、TP 通道 goal_failed 规则触发、自动进入 badcase 池，全程无人工拦截。

🟢最需要人工介入的白盒点
  1. Tag Taxonomy 定义 — 不同业务场景的关键能力维度不同，当前是代码写死
  2. FN / Uncertainty 案例确认 — 这两类案例的质量决定 benchmark 的信噪比
  3. severityScore 权重 — 当前加法权重写死，需业务方参与校准
  4. 回归判定标准 — ValidationRun 的 pass/fail 阈值需人定义
